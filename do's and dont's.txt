

Do’s (Best Practices)
- Always modularize
- add good documentaion
- describe the functionality
- check dependencies of files
- stick to the directroty structure
- give logical file names

Write tests alongside features
Ensure every module or function has basic unit tests or integration tests.

Follow a consistent coding style
Use formatting tools like black, prettier, or clang-format and stick to naming conventions (e.g., snake_case or camelCase consistently).

Use clear, descriptive variable/function/class names
Avoid generic names like foo, temp, or data123.

Refactor regularly
Break large blocks into reusable components/functions when patterns emerge.

Add error handling and logging
Always check edge cases, and log meaningful messages to aid debugging.

Keep context and reasoning in comments
Use comments to explain why something is done, not just what it does.

Version control code and prompts
Save both code and LLM prompts that generated critical logic for traceability.

Specify inputs and outputs clearly
Especially for LLM-assisted code, define expected types, shapes, and formats.

Annotate with type hints (where possible)
Improves readability and reduces LLM hallucination in type inference.

❌ Don’ts (Avoid These Mistakes)
- Do not over complicate
- No 1000 line code
- No redundant code
- No illogical file naming convetions
- No hard coding
- do not create unncecessary files and folders
Don't rely on the LLM without reviewing output
Always test and inspect LLM-generated code critically.

Don't ignore security implications
Avoid using hardcoded secrets, unvalidated inputs, or risky eval-type logic.

Don't allow silent failures
Every catch should log something meaningful or raise informative errors.

Don't ignore performance bottlenecks
If an LLM suggests a brute-force or inefficient solution, seek optimization.

Don't keep outdated or dead code
Remove commented-out code or unused functions after refactoring.

Don't copy-paste without understanding
Developers should understand and validate all code introduced by the LLM.

Don’t forget to update documentation when code changes
Out-of-sync docs are worse than none at all
