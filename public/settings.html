Email / SMTP

Configure the outbound mail server used by alert notifications. These settings become the system-wide fallback — individual alert channels can override them.

How Email / SMTP works

ezHealthKonnect uses SMTP to send alert notification emails (threshold breaches, interface errors, system events). Configure your mail server here once and all alert channels will use it automatically.

  • SMTP Host / Port — your mail server address. Common: smtp.gmail.com:587, smtp.office365.com:587, or your on-premises relay.
  • TLS / STARTTLS — enable for ports 587 (STARTTLS) or 465 (SSL). Disable only for internal relays on port 25.
  • From Address — the envelope sender; use a monitored mailbox so bounce-backs are visible.
  • Test Email — sends a live test message immediately; does not save settings first.
Save before testing. Credentials are encrypted with AES-256-GCM before storage — they are never returned in plain text after saving.

Security & Access

Authentication policies, session lifetimes, and account lockout rules. JWT expiry and login lockout apply on the next login. Session timeout applies after a Node.js restart.

How Security & Access works

These settings control how long users stay logged in and how the system reacts to repeated failed login attempts.

  • JWT Expiry — API tokens expire after this many hours. Short values (1–4 h) are recommended for HIPAA environments. Changes affect tokens issued after saving.
  • Session Timeout — browser sessions expire after this many minutes of inactivity. Takes effect after the Node.js process restarts (or the next user login).
  • Max Login Attempts — after this many consecutive failures the account is locked for the lockout duration. Set to 0 to disable lockout.
  • Lockout Duration — minutes an account stays locked. Admins can manually unlock via User Management.
HIPAA Security Rule (§164.312) requires automatic log-off. A session timeout of 15–30 minutes is typical for clinical workstations.

HL7 / FHIR Processing

Default message processing parameters. Applied when a message or interface does not specify its own version or validation policy. Changes are picked up within 5 minutes (settings cache TTL).

How HL7 / FHIR Processing works

These are system-wide defaults. Every interface and pipeline step can override them individually — these values only apply when no interface-level setting exists.

  • Default HL7 Version — used by the parser when the MSH-12 field is missing or unrecognised. Most modern EHRs send v2.5.1; older systems may send v2.3 or v2.4.
  • Validation Level — None: accept anything; Basic: check required segments; Strict: enforce full HL7 spec (may reject malformed ADTs from legacy systems).
  • Default FHIR Version — R4 is the current standard. STU3 is still used by some older Epic/Cerner endpoints.
  • Strict FHIR Validation — when enabled, outbound FHIR bundles are validated against the official FHIR JSON Schema before delivery.
Schema Packages (see Schema Packages tab) provide richer segment descriptions and field-level validation. Without them, the parser falls back to built-in minimal definitions.

Message Queue & Processing

Controls queue capacity, message retention, and processing concurrency. Read by the processing engine via the AppSettingsCache (5-min TTL).

How Message Queue works

The in-memory processing queue buffers incoming messages between inbound connectors and the transformation pipeline. These settings prevent memory exhaustion and data loss during traffic spikes.

  • Queue Size — maximum messages held in memory. When full, the TCP/MLLP ACK mode determines whether to NACK or block the sender.
  • Max Workers — parallel goroutines processing messages simultaneously. Higher values improve throughput on multi-core hosts but increase DB connection pressure.
  • Message Retention — how many days processed messages are kept in interface tables before automatic cleanup. Shorter = lower DB disk usage.
  • Retry Delay / Max Retries — applies to built-in step-level retry; individual pipeline steps can override these per step.
Settings are cached for 5 minutes. Changes take effect on the next cache refresh — no restart required.

Connector Defaults

Global fallback values applied when a connector instance has no per-connector timeout override. Read from services.GetAppSettings().GetConnectorDefaultSettings() at connector initialization.

How Connector Defaults work

These values are the last-resort fallback for all 32 connector types. Each connector can override them in its own configuration panel under Interfaces → Edit → Connectors.

  • Connect Timeout — seconds to wait while establishing a connection (TCP handshake, DB connect, etc.). Increase for slow WAN links.
  • Read Timeout — seconds to wait for the first byte of a response after connecting. Relevant for HTTP REST and database query connectors.
  • Write Timeout — seconds allowed to send a full message. Critical for large FHIR bundles over slow links.
  • Max Connections — cap on concurrent outbound connections per connector instance. Protects downstream systems from being overwhelmed.
Changes apply at the next connector initialization — new connectors started after saving will pick up the new defaults immediately.

Alert Defaults

Default thresholds and retention policies. These values pre-fill the New Alert Rule form — each rule can still be customised individually after creation.

How Alert Defaults work

These defaults only matter when you create a new alert rule — existing rules are unaffected. Think of them as a template for your typical thresholds.

  • Error Rate Threshold (%) — percentage of messages that must fail within the evaluation window before an alert fires. Lower = more sensitive.
  • Evaluation Window (min) — rolling time window for rate calculations. A 5-min window catches spikes; a 60-min window smooths out brief outages.
  • Alert Cooldown (min) — minimum time between repeated notifications for the same rule. Prevents alert fatigue during sustained outages.
  • Alert Retention (days) — how long fired alert records are kept in the audit table before cleanup.
Alert notifications are delivered via the SMTP server configured in Email / SMTP. Make sure that section is configured before enabling alert rules.

Performance & Tuning

Go backend tuning parameters. Log level is applied immediately. DB pool changes require a Go backend restart.

How Performance tuning works

These settings tune the Go processing engine. Incorrect values can starve the database or flood logs — start conservatively and increase based on monitoring data.

  • Log Level — error (quiet), warn, info (recommended for production), debug (verbose — logs every segment parse). Applied immediately.
  • DB Pool Min/Max — PostgreSQL connection pool size. Max should not exceed your Postgres max_connections setting (default 100). Requires Go backend restart.
  • Goroutine Limit — maximum concurrent pipeline executions. Higher values improve throughput but increase memory pressure under load.
  • Metrics Interval — how often the Go backend samples internal counters (queue depth, goroutines, memory). Affects Monitoring page refresh granularity.
In Docker, the Go backend restarts automatically (the compose command has a while true; do ./go-api; done restart loop). Pool changes take effect within ~5 seconds.

Object Storage

Configure where raw messages, parsed content, and processing logs are stored. Changes apply immediately without a restart.

How Object Storage works

Raw HL7 messages, parsed JSON content, and large processing logs are stored in object storage (not in PostgreSQL) to keep the database lean and support unlimited retention.

  • Local driver — files written to /app/storage inside the container. Simplest for development; data is lost if the volume is removed.
  • S3 / MinIO driver — recommended for production. The bundled MinIO container (http://minio:9000) is S3-compatible. Use your cloud bucket for production deployments.
  • Bucket — the bucket must already exist. ezHealthKonnect will not auto-create it; run mc mb local/ezhealthkonnect on first MinIO setup.
  • Path-style endpoint — leave enabled for MinIO and self-hosted S3. Disable for AWS S3 (uses virtual-hosted URLs).
Switching drivers mid-production does not migrate existing data. Archive existing messages first, then switch the driver and restart.

Git Integration

Version-control your interface and pipeline configurations. Connect a GitHub, GitLab, Bitbucket, or self-hosted Git repository — then commit changes directly from the pipeline builder.

How Git Integration works

When Git is connected, every Save action in the Pipeline Builder can optionally commit the interface bundle to your repository. This gives you a full change history, PR-based review workflow, and disaster recovery.

  • Bundle format — each interface is serialised as interfaces/{slug}/bundle.json containing the pipeline steps, connector configs, and metadata.
  • Personal Access Token — create a repo-scoped token in GitHub/GitLab. Only repo (read+write) scope is needed. Stored encrypted with AES-256-GCM.
  • Branch — target branch for auto-commits. Using a dedicated branch (e.g., ehk-configs) keeps interface changes separate from application code.
  • Auto-commit — when enabled, every Pipeline Builder save triggers a commit. Disable to only commit manually via the builder's "Commit to Git" button.
The repo does not need to be dedicated to ezHealthKonnect — you can use a monorepo alongside your application code as long as the token has push access.

AI Assistant (ezCompanion)

On-premise AI for script generation, mapping suggestions, and message trace analysis. All inference runs locally via Ollama — no PHI leaves the network.

How the AI Assistant works

ezCompanion is powered by Ollama, a local LLM inference server. All model calls stay inside your Docker network — messages and PHI are never sent to external AI APIs.

  • Chat Model — used for script generation, natural language queries, and pipeline suggestions. llama3.2:3b is the default (fast on CPU-only). Switch to llama3.2:8b for higher quality on GPU hosts.
  • Embedding Model — used for semantic search over your message archive and HL7 dictionary. nomic-embed-text is the recommended default.
  • Ollama Host — the URL of the Ollama inference server. In Docker Compose this is http://ollama:11434. Change if using a remote GPU server.
  • Context Window — maximum tokens sent to the model per request. Larger windows allow richer analysis but use more memory. 4096 is safe for most systems.
Models are downloaded automatically by ollama-init on first startup. Subsequent starts use the cached models from the ollama_data Docker volume — no internet required.

Schema Packages

Download and manage HL7 and FHIR schema definitions. Only install what your interfaces actually need — each pack is independent. Schemas are downloaded from the ezInterop Solutions schema registry and stored locally.

How Schema Packages work

Schema packages provide rich segment descriptions, field-level validation rules, and FHIR profile definitions used by the HL7 parser and FHIR transformation engine. Without them the system falls back to minimal built-in definitions.

  • HL7 packages (v2.3 – v2.9) — enable human-readable field names, data type validation, and the segment dictionary used in the HL7 Reader and pipeline condition builder.
  • FHIR packages (R4, STU3, R5) — provide resource profiles, value set bindings, and JSON Schema validation for outbound FHIR bundles. Required for Strict FHIR Validation.
  • Install source — packages are looked up first in the local schema-dist/ folder (offline/dev mode), then from the GitHub Releases registry. Internet access is only needed when the local copy is absent.
  • Storage — installed packages are extracted to /app/schemas/ inside the container (the ./schemas volume mount). They persist across restarts.
For air-gapped installations, copy the ezhealthkonnect-schemas repo to the host alongside the main project — the app will find and use local zips automatically without internet access.
